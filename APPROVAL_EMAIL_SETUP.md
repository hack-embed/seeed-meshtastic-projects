# Automatic project approval emails

The website can encrypt a maker’s contact address in the browser and attach the encrypted value to the public GitHub issue. After an AE-approved project has been validated and saved to the catalog, GitHub Actions decrypts that contact and sends an approval email through Resend. L2 approval emails also link to `l2.html#submit-social` and explain that optional social sharing can earn the Share Reward.

**This checkout is not configured to send mail.** No keys or mail service have been created. Until setup is complete, the forms offer the existing private email handoff. Addresses submitted through that manual handoff are not available to the automated workflow, and older submissions without encrypted contact cannot receive automatic approval emails.

## Enable the service

1. Create or use a Resend account and verify a sending domain. Choose an approved sender address, for example `Mesh Lab <mesh-lab@your-verified-domain.example>`. Resend must be able to send to real recipients; its testing sender is not sufficient for production.
2. Generate an RSA key pair in a secure directory outside this repository. Keep the private key out of Git, issue bodies, browser configuration, screenshots, and logs:

   ```sh
   openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out approval-private.pem
   openssl pkey -in approval-private.pem -pubout -out approval-public.pem
   ```

3. Add repository **Actions secrets**:

   | Secret | Value |
   | --- | --- |
   | `APPROVAL_EMAIL_PRIVATE_KEY` | Entire private PEM, including its header, footer, and line breaks |
   | `RESEND_API_KEY` | A sending API key for the verified domain |

4. Add repository **Actions variables**:

   | Variable | Value |
   | --- | --- |
   | `APPROVAL_EMAIL_FROM` | Verified sender address, optionally with its display name |
   | `MESH_LAB_SITE_URL` | Canonical HTTPS site root, e.g. `https://hack-embed.github.io/seeed-meshtastic-projects/` |

5. Edit `docs/notification-config.js`: set `enabled: true`, choose a stable `keyId`, and paste the entire **public** PEM into `publicKeyPem` using a JavaScript template literal. Never paste the private PEM or mail API key here. A public key is intentionally public. The workflow checks that its private key matches this public key before processing recipients.
6. Deploy the site and confirm GitHub Actions has permission to write to the default branch. Its durable notification ledger is created at `.github/data/approval-notifications.json`. Existing repository branch rules must permit these bot commits as well as catalog updates.
7. Test with a project and address you control. Submit through the site, verify that its public issue contains `Private Approval Contact` with a `mesh-contact-v1.` value and no readable email, then approve the project through the normal AE workflow. Check the recipient inbox and the notification job. Run the workflow again: the project should report `already-sent`.

Do not paste a plain email into GitHub’s native issue form. The private contact envelope is generated by the website form. Native GitHub submissions without an envelope remain eligible for the catalog but do not trigger an email.

## Delivery, retries, and failure handling

- The catalog workflow first publishes only validated submissions approved by an authorized reviewer. Its separate notification job then checks the current issue still has `ae-approved`, matches the published project, and has decryptable contact bound to that project’s title and author.
- The scheduled hourly run and manual workflow dispatch also process previously published projects. This retries temporary failures and supports adding an encrypted contact after an earlier submission.
- A durable `pending` ledger entry is written to GitHub **before** calling the mail provider. If that write fails, no email is attempted. Only a provider acknowledgment followed by a successful ledger write produces `sent`.
- The provider uses one stable idempotency key per repository/project. Retrying a timeout or a crash after delivery uses that same key and payload. The ledger stores only issue numbers, timestamps, randomized-ciphertext/message digests, and delivery IDs; it contains no addresses or message bodies.
- Resend retains idempotency keys for 24 hours. A pending attempt older than **23 hours**, a changed contact, or a changed email payload produces `NOTIFICATION_REQUIRES_RECONCILIATION` and sends nothing. This avoids guessing whether a previous attempt delivered after the provider’s protection expires.
- To reconcile, look up the project’s stored idempotency key or provider delivery in the Resend dashboard. If it was delivered, update that ledger entry to `{"status":"sent","sentAt":"<ISO timestamp>","providerId":"<confirmed ID>"}`. Only after confirming **no delivery occurred**, remove that project’s pending entry and manually rerun the catalog workflow. Never delete an ambiguous entry just to clear a warning.
- `sent` prevents repeat emails even if a project is reapproved or its contact changes. One approval email is sent per project; updates do not trigger another approval email.
- Email failures are visible as a failed notification job and safe per-project warning codes. They do not block deployment of the reviewed catalog. Review this job separately if a recipient reports missing mail. Successful API acceptance does not prove inbox delivery; check provider delivery/bounce records.

Missing service settings, mismatched keys, invalid envelopes, or submissions edited since approval fail closed. Error messages deliberately exclude addresses, decrypted payloads, mail API response bodies, and private keys.

## Privacy and contact handling

The browser uses AES-256-GCM for the contact payload and wraps its random key with RSA-OAEP/SHA-256. The encrypted payload is bound to the submitted project’s title and author. A copied token cannot be reused for a project with different identifying fields. The email is never stored in browser storage or the public catalog. Ciphertext is public and remains in issue history, so retain and protect the private key accordingly.

Entering an address does not verify ownership of that mailbox. AE still reviews the project and attribution. Notifications contain only the project title and links derived from the configured Mesh Lab domain, and do not embed user-submitted resource URLs or HTML.

The social reward form stores the same private envelope bound to the selected project’s title and author. It does not itself trigger an approval email or verify a reward claim. Resend also receives the address when an approval email is sent, under the team’s mail-service account and retention settings.

### Read a social reward contact locally

An authorized maintainer can use `scripts/read-private-contact.mjs` on a secure local machine. Required inputs are the downloaded social issue JSON, the selected project’s catalog ID, and the private PEM file. The project must already exist in the local approved catalog; pull the latest catalog first. The social issue’s `Approved Project Submission` must reference that same project’s GitHub issue. The encrypted `Private Approval Contact` must be intact.

For example, using an existing secure directory **outside this checkout**:

```sh
gh api repos/hack-embed/seeed-meshtastic-projects/issues/84 > /secure/path/share-84.json
node scripts/read-private-contact.mjs --issue /secure/path/share-84.json --project community-42 --private-key /secure/path/approval-private.pem --out /secure/path/contact-84.json
```

Replace the example issue/project numbers and paths. The utility writes a **new** contact JSON file with owner-only permissions (`0600`), refuses outputs inside the repository, refuses to overwrite an existing file, and never prints the address or key. Open that local file for authorized reward follow-up, then remove it when no longer needed. Do not run this utility in public Actions jobs or paste contact data into GitHub issues. It also supports the original project submission issue by using its matching catalog ID.

Changing the project title or author after the website encrypted the contact invalidates the binding. Regenerate the submission through the website with the final fields or collect the contact privately; do not disable the binding check to read a mismatched token.

Keep a secure backup of the private key. This minimal implementation supports one active key. Replacing it immediately makes previous encrypted contacts unreadable; process or privately migrate pending contacts before rotating. The `keyId` must change when the key changes. To stop sending, set `enabled: false` and deploy; remove service credentials if needed. Keep the ledger so re-enabling does not resend past notifications.

## Local verification

```sh
node --test tests/approval-notifications.test.mjs
```

The tests generate temporary keys in memory and use a mock sender. They cover browser/Actions encryption compatibility, tampering and identity checks, eligibility, absence of public contact, durable reservation failures, repeat runs, ambiguous delivery retries, post-send ledger failures, retry expiry, L2 email copy, maximum submission size, and safe local contact files. They do not send real email or create repository state.
